## 1. Problem statement

Papers on LLM-based RTL generation usually report one pass@k or one area figure. The prompt wording, the rule used to pull code out of the model response, the handling of module names, the sampling seed and the synthesis script are often only partly stated. Existing work handles run-to-run variation by repeating runs; it does not usually measure how large each source of variation is. The survey's Section V-E lists nine items a paper "should report" but gives no evidence on which of them matter.

This project turns that list into a measurement.

## 2. Objective

**Primary objective.** On a fixed 60-problem subset of VerilogEval v2 (spec-to-RTL), measure how far pass@1 and a synthesized gate-count proxy move when exactly one evaluation variable is changed and all others are held fixed, then rank the variables by effect size.

**Deliverables**

1. An open harness (`rtlsens`) that runs the full chain: generate, extract, compile and simulate, synthesize, analyze.
2. A results package: tables T1–T7 and figures F1–F4 (Section 11).
3. A run-manifest schema (JSON) listing the variables that were found to matter, ordered by measured effect.
4. A 4–6 page write-up (Section 15).

**Measurable success criteria**

| ID | Criterion |
|---|---|
| S1 | All acceptance tests in Section 12 pass. |
| S2 | Every number in T1–T7 is regenerated by one command from raw records. |
| S3 | For each of the 5 factors (Seed, P, X, N, Y), the study states a verdict: *material* or *not distinguishable from noise*, using the rule in Section 3. Seed is the noise reference itself, so its verdict is its measured σ_seed. |
| S4 | The manifest in Section 8.1 is complete for every run (no null in required fields). |

**Non-goals.** Proposing a new generation method. Claiming results for commercial tools, other benchmarks, or models beyond the two chosen. Measuring silicon area, power or timing (the study uses a unit-less gate-count proxy only).

## 3. Research questions, hypotheses, decision rule

**Decision rule ("material").** A factor is *material* when its effect on pass@1, |Δ|, is at least twice the seed standard deviation σ_seed (Section 9) **and** the 95% bootstrap CI of Δ excludes 0. Otherwise it is reported as *not distinguishable from noise at this sample size*.

| RQ | Factor | Hypothesis (prior, to be tested) | Reported as |
|---|---|---|---|
| RQ1 | Sampling seed | Run-to-run σ of single-run pass@1 matches the binomial prediction √(mean_i p_i(1−p_i) / N) within a factor of 2. | σ_seed observed vs predicted (T2) |
| RQ2 | Prompt wording (neutral rewrite P1) | Aggregate Δ is within noise, but individual problems flip more often than seed noise alone explains. | Δ with CI; excess flip rate (T3) |
| RQ3 | Code-extraction rule (X) | Matters only for samples with several code blocks or text around the code; size depends on the model. | Δ and flips (T3) |
| RQ4 | Module-name handling (N) | No directional prior. The prompt fixes the name `TopModule`, so renames may be rare. | Δ and flips (T3) |
| RQ5 | Model ranking stability | If the gap between two models is under about 2σ_seed, a single-run comparison reverses with non-trivial probability. | ρ (T4) |
| RQ6 | Yosys script (Y) | Absolute gate counts change by large factors between scripts; relative model ordering is more stable. | Medians, ordering flips (T5) |
| RQ7 | Determinism at temperature 0 | Same seed and same hardware gives identical outputs; this also tests that the seed is passed through correctly. | Identity rates (T6) |

Pre-flight evidence for RQ6 (reference solutions, not LLM output): `Prob030_popcount255` synthesizes to 1351, 4263 and 3324 cells under scripts Y0, Y1 and Y2 respectively; `Prob044_vectorgates` gives 14, 14 and 11; `Prob039_always_if` gives 2, 2 and 5.

## 6. Experimental design

### 6.1 Problem set (validated)

VerilogEval v2 `spec-to-rtl` has 156 problems. A problem is **eligible** only if all four conditions hold; each exclusion was measured on the reference solutions:

| Exclusion rule | Why | Problems removed |
|---|---|---|
| Reference fails the harness's own classification when used as the DUT | Even a perfect answer would be scored as a failure. Cases: 3 print `TIMEOUT` (`Prob082_lfsr32`, `Prob141_count_clock`, `Prob156_review2015_fancytimer`); 1 does not compile against its own testbench (`Prob099_m2014_q6c`: testbench expects ports `Y2`, `Y4` the reference lacks). | 4 |
| Yosys 0.33 frontend rejects the reference (`read_verilog -sv`) | No cell count possible. The seven are state-machine problems: `Prob095_review2015_fsmshift`, `Prob096_review2015_fsmseq`, `Prob137_fsm_serial`, `Prob146_fsm_serialdata`, `Prob151_review2015_fsm`, `Prob152_lemmings3`, `Prob155_lemmings4`. | 7 |
| Reference synthesizes to 0 cells | Pure wiring; area comparison is meaningless. | 13 |
| Prompt does not start with the standard sentence | The P1 rewrite rule (6.6) would not apply. | 4 |

**Eligible: 128 problems.** The study uses a **60-problem subset**, drawn with `random.Random(42).sample(sorted(eligible), 60)` on Python 3.12.3. The resulting list is frozen in Appendix A and in `configs/problem_subset.txt`; the code must reproduce it exactly, and a unit test compares the two.

### 6.2 Systems under test

Two models, M_A and M_B, from different families, served by the same Ollama instance. Quantization, Ollama version, model digest and hardware are written into the manifest. Reasoning models that emit thinking text are avoided, since they change what extraction has to handle.

### 6.3 Factors and levels

Generation-side factors need new LLM calls. Evaluation-side factors re-score the **same** saved responses, so they carry no sampling noise.

| Group | ID | Factor | Levels |
|---|---|---|---|
| Generation | Model | system under test | M_A, M_B |
| Generation | Seed | sampling seed | `seed_k = 1000 + k`, k = 0..9 (10 levels) |
| Generation | P | prompt wording | **P0** original; **P1** neutral rewrite (6.6) |
| Evaluation | X | code extraction | **X0** first fenced block; **X1** last fenced block; **X2** first `module … endmodule` span in raw text, ignoring fences |
| Evaluation | N | module-name handling | **N0** strict (use code as is); **N1** if the code has exactly one `module <name>` and the name is not `TopModule`, rename that identifier to `TopModule` |
| Evaluation | Y | Yosys script (cell count only) | **Y0** `synth`; **Y1** `synth -noalumacc`; **Y2** `proc; opt; techmap; abc -g AND,NAND,OR,NOR,XOR,XNOR` (scripts in Section 7) |

### 6.4 Configurations (one factor at a time around a baseline)

Baseline **B0 = (P0, X0, N0)**, sampled at temperature 0.85, top_p 0.95 (VerilogEval's published high-temperature setting).

| Config | P | X | N | Samples scored | Purpose |
|---|---|---|---|---|---|
| B0 | P0 | X0 | N0 | 10 per problem | baseline and seed spread |
| P1 | P1 | X0 | N0 | 10 per problem | prompt effect |
| X1 | P0 | X1 | N0 | same as B0 | extraction effect |
| X2 | P0 | X2 | N0 | same as B0 | extraction effect |
| N1 | P0 | X0 | N1 | same as B0 | naming effect |
| T0-A, T0-B | P0 | X0 | N0 | 1 per problem, run twice | determinism at temperature 0 (T=0, top_p 0.01, seed 0) |

Y0/Y1/Y2 are applied to every sample that passes under B0, and to the 60 reference solutions.

### 6.5 Counts and cost

| Item | Count |
|---|---|
| Generations | 2 models × 60 problems × (10 samples × 2 prompts) = 2,400; plus determinism runs 2 × 60 × 2 = 240; **total 2,640** |
| Simulations (before de-duplication) | per model 600×4 (B0, X1, X2, N1) + 600 (P1) + 120 = 3,120; **6,240 total** |
| Yosys runs | at most 600 passing samples × 3 scripts × 2 models, plus 180 reference runs |
| Output tokens | about 2,640 × 250–400 = 0.7–1.1 M |
| Generation time | about 5–10 h on one 8 GB GPU at 30–40 tok/s sequential; run 2–4 requests in parallel (`OLLAMA_NUM_PARALLEL`) to shorten |
| Evaluation time | 156 reference simulations took 11 s in pre-flight, so 6,240 take roughly 7–10 min single-threaded |

**Fallback levers, in this order, if generation is too slow:** reduce samples 10 → 5; reduce problems 60 → 40 (first 40 of Appendix A); drop P1 for M_B; replace one model with an API model. State any reduction in the paper.

### 6.6 Prompts and generation parameters

The system prompt is deliberately light on format instructions, to reflect common practice, so that extraction rules have something to disagree about. Exact text in Appendix B.

- **P0** user message: the problem's `_prompt.txt`, verbatim, stripped of leading and trailing whitespace.
- **P1** user message: P0 with this regex replacement applied once: `I would like you to implement a module named TopModule with the following\s+interface\.` → `Please write a SystemVerilog module named TopModule that has the following interface.` All other text unchanged.
- Parameters: `max_tokens = 1024` (VerilogEval default), `temperature = 0.85`, `top_p = 0.95`, `seed = 1000 + k`. Determinism runs: `temperature = 0`, `top_p = 0.01`, `seed = 0`.

| Stage | Command (planned CLI) | Reads | Writes |

| 0 | `python -m rtlsens.cli preflight` | tools on PATH | `versions.lock.txt`, `manifest.json` |
| 1 | `python -m rtlsens.cli subset` | `dataset_spec-to-rtl/` | `problem_subset.txt` (must equal Appendix A) |

**Compile and simulate (exact, from the VerilogEval Makefile):**

```
iverilog -Wall -Winfloop -Wno-timescale -g2012 -s tb -o <bin> <dut.sv> <problem>_test.sv <problem>_ref.sv
timeout 30 vvp <bin>
```

The DUT module must be named `TopModule`; the testbench instantiates the reference as `RefModule`.

**Outcome classification (mirrors `scripts/sv-iv-analyze`).** Compile log and simulation output are read together:

| Class | Rule | Harness code |
|---|---|---|
| NO_CODE | extraction returned nothing | (ours) |
| COMPILE_ERROR | `syntax error`, any `error` line, `Unknown module type`, `Unable to bind`, never-triggering always blocks, etc. | `S e 0 n w m p c C` |
| TIMEOUT | the line `TIMEOUT` appears, or `vvp` exceeds 30 s | `T` |
| MISMATCH | line `Mismatches: <n> in <m> samples` with n > 0 | `R` (or `r` when the code mentions `posedge reset`, `negedge reset` or `posedge r)`) |
| OTHER | no decisive line at all (for example the simulator produced no result line) | `R` / `r`, as above |
| PASS | `Mismatches: 0 in <m> samples`, and no error or TIMEOUT line | `.` |

A sample counts as correct only for class PASS. The harness reads the compile log and then the simulation output line by line, and the first decisive line wins; the reimplementation must keep that behaviour. The harness lumps MISMATCH and OTHER under `R`/`r`; we split them only to report how often each occurs, and the split never changes whether a sample passes.

**Yosys scripts (validated to run; the module key in the JSON is `\TopModule`, so read the first value of `modules`):**

```
Y0:  read_verilog -sv dut.sv; synth -top TopModule; tee -q -o out.json stat -json
Y1:  read_verilog -sv dut.sv; synth -top TopModule -noalumacc; tee -q -o out.json stat -json
Y2:  read_verilog -sv dut.sv; hierarchy -top TopModule; proc; opt; techmap;
     abc -g AND,NAND,OR,NOR,XOR,XNOR; opt_clean; tee -q -o out.json stat -json
```

Cell count = `num_cells`. It is a **gate-count proxy**, not area: no liberty file is used.

## 9. Metrics (exact definitions)

Let N = 60 problems, K = 10 samples, `o_{i,k}` ∈ {0,1} the PASS indicator for problem i, sample k under a given configuration.

1. **pass@1** = (1 / NK) Σ_i Σ_k o_{i,k}. This is the mean per-sample pass rate (unbiased pass@1).
2. **Seed-run pass@1**: r_k = (1/N) Σ_i o_{i,k}. **σ_seed** = sample standard deviation (ddof = 1) of r_0..r_9; also report min and max. This is the spread a single-run paper would see.
3. **Predicted σ_seed** = √( (1/N²) Σ_i p̃_i (1−p̃_i) ), with p̃_i = p̂_i(1−p̂_i)·K/(K−1) as the unbiased variance term and p̂_i = (1/K) Σ_k o_{i,k}. Worked example: if the mean of p̂_i(1−p̂_i) is 0.08, then σ ≈ √(0.08/60) = 3.7 percentage points. If observed σ falls outside 0.5×–2× of predicted, investigate before reporting.
4. **Confidence intervals**: percentile bootstrap over problems, 10,000 resamples, RNG seed 12345, 95%.
5. **Factor effect** Δ_f = pass@1(config f) − pass@1(B0), with a bootstrap CI. Apply the rule of Section 3.
6. **Flip rate, evaluation-side factors**: fraction of the N·K samples whose PASS indicator differs between config f and B0, reported as gains (fail → pass) and losses (pass → fail) separately.
7. **Flip rate, prompt factor**: F_P = (1/NK) Σ_{i,k} 1[o^{P0}_{i,k} ≠ o^{P1}_{i,k}]. Seed baseline F_S = mean over ordered pairs k ≠ k′ of (1/N) Σ_i 1[o^{P0}_{i,k} ≠ o^{P0}_{i,k′}]. **Excess flip** = F_P − F_S, with bootstrap CI.
8. **Ranking**: Δ_AB(e) = pass@1(M_A, e) − pass@1(M_B, e) for each config e; report the sign for every config. **Single-run reversal probability** ρ = (1/K²) Σ_{k,k′} 1[sign(r^A_k − r^B_{k′}) ≠ sign(Δ_AB(B0))], counting ties as 0.5.
9. **Gate-count proxy** (only samples that PASS under B0, only problems where the reference has > 0 cells under that script): ratio ρ_y(s) = cells_y(s) / cells_y(ref); tool-induced change δ(y→y′) = cells_y′(s) / cells_y(s) − 1, median and IQR; seed-induced spread = per-problem coefficient of variation of cells_Y0 across passing samples; ordering stability = fraction of problems (both models with at least one passing sample) where the model with the lower median ρ differs between Y0 and Y2.
10. **Determinism**: raw-identity rate = fraction of (model, problem) pairs whose `raw_response` is byte-identical between T0-A and T0-B; outcome-identity rate = same for the PASS indicator.

### 11.2 Priors

- **σ_seed.** Expected to be a few percentage points. It follows from item 3 of Section 9 and will be checked against that formula.
- **pass@1 level.** Likely in the tens of percent for 7–8B models on this benchmark (the VerilogEval v2 revision paper reports about 34% for a 6.7B domain-specific model; check its exact setting before citing). The level matters less than the differences.
- **Evaluation-side factors.** Exact by construction: they re-score identical responses, so any Δ is a pure harness effect.
- **Y scripts.** Large for arithmetic-heavy designs (the popcount reference changes by about 3× across scripts), near zero for tiny gate-level designs.

### 11.3 How to read outcomes

| Observed pattern | Conclusion to state |
|---|---|
| All generation-side Δ within 2σ_seed; evaluation-side Δ small | Single-run reporting is adequate for these factors at this scale; reporting priority is low. This is a valid, publishable result. |
| N or X material for at least one model | Harness post-processing rules must appear in the manifest; they can change the headline number without any change to the model. |
| ρ well above 0 for the observed model gap | Single-run model comparisons at this N are unreliable; report CIs or multiple seeds. |
| Excess flip rate > 0 with CI excluding 0 although Δ is within noise | Prompt wording changes which problems pass without changing the average; per-problem claims need prompt controls. |
| Y changes absolute counts by large factors but ordering stable | Report the script; compare models only within one script. |

## 12. Acceptance tests ("working" criteria)

| ID | Test | Pass condition |
|---|---|---|
| A1 | `preflight` | iverilog 12.x and Yosys found; versions written to the lock file |
| A2 | **Oracle**: a stub model returns each reference solution (renamed `TopModule`) inside a fenced block | 60 of 60 PASS under every (X, N) config |
| A3 | **Negative controls**: stub returning an empty module; stub returning prose with no code | 0 of 60 PASS; prose stub gives 60 of 60 NO_CODE |
| A4 | Run stage 3 twice | `eval.csv` byte-identical (equal SHA-256) |
| A5 | Unit tests (`pytest`) | all pass: extraction, P1 rewrite, classification, subset equals Appendix A |
| A6 | Manifest validation | all required fields non-null |
| A7 | Count integrity | for each config, class counts sum to N·K (or N for determinism runs) |
| A8 | Cache check on 20 random samples, with and without the cache | identical outcomes |
| A9 | Seed passthrough | two different seeds at T = 0.85 give different text for some problems; T0-A and T0-B identical or the difference is reported |
| A10 | Fresh clone | `selftest` then the full chain on 3 problems finishes without manual steps |

**Pre-flight results already obtained (reference solutions as DUT, harness rules, 156 problems, 11 s total):** 152 PASS, 3 TIMEOUT, 1 COMPILE_ERROR. Yosys 0.33 accepted 148 of the 156 reference solutions after the rename to `TopModule` and rejected 8 (seven of them are the Yosys exclusions in 6.1; the eighth, `Prob156_review2015_fancytimer`, is already excluded by the self-test TIMEOUT); 13 of the 148 accepted ones have zero cells.

## 13. Risks and mitigations

| Risk | Effect | Mitigation |
|---|---|---|
| GPU or server differences change outputs between runs | Seeds not reproducible across machines | Run everything on one machine; record hardware and Ollama version; A9 detects problems early |
| Seed ignored by the endpoint | Seed spread measures nothing | A9 before the full run; if seeds are ignored, use the native `/api/chat` `options.seed` path |
| CPU-only machine | Generation takes days | Use the fallback levers in 6.5 |
| Model emits reasoning or extra prose | Extraction effects dominate | Choose non-reasoning models; this is also what X1 and X2 are meant to expose |
| Weak models pass very few problems | Wide CIs; cell-count analysis starved | Report anyway; choose the stronger of two candidate models in the smoke run |
| Yosys rejects model code that iverilog accepts | Missing cell counts | Record `ok = false`; report the fraction; do not impute |
| Dataset defects at the pinned commit | Wrong denominators | Self-test gate (6.1); record commit hash |
| Scope creep (adding PPA tuning, repair loops, more models) | Misses the 2-day budget | Anything not in Section 6 is a follow-up |

## 14. Limitations to state in the paper

- 60 problems from one benchmark and two models; the CIs are correspondingly wide.
- The subset excludes 28 of 156 problems (self-test failures, Yosys-rejected FSMs, zero-cell designs, non-standard prompts), so results do not extend to those categories.
- One factor is varied at a time; interactions are not measured.
- Gate count from Yosys without a cell library is a proxy; it is not area, timing or power.
- Determinism is claimed only for one machine and one server version.
- Open-source tools only (Icarus, Yosys); commercial tool sensitivity is untested.
- The system prompt format instruction is deliberately light; a strict format instruction would likely shrink the extraction effects and is a follow-up.

## Appendix D — Implementation notes (v0.2, after building the harness)

The harness in `llm-rtl-sensitivity/` follows this document. Differences and additions, each found while building or testing:

| # | Change | Reason |
|---|---|---|
| D1 | Added `backends.py` (OpenAI-compatible client plus stub models), `evaluate.py` (stages 3–4 orchestration), `acceptance.py`; one results directory per config (`results/main`, `results/selftest`, `results/planted`). | Section 5 tree had no place for stubs or stage orchestration. |
| D2 | Extraction rule X2 requires `(`, `;` or `#` after the module name. | A unit test showed a prose line beginning with "module is a keyword" was captured as code. |
| D3 | T3/T7 verdicts have three levels: *material* (rule of Section 3, unchanged), *detectable, below 2σ_seed* (CI excludes 0), *not distinguishable from noise* (CI includes 0). | Evaluation-side factors re-score identical responses, so a 5 pp shift with a CI excluding 0 is a real harness effect even when it is under 2σ_seed. The two-level wording would have called it noise. |
| D4 | The simulation cache key is `(problem, code_sha256)`. | The hash is taken after the N rule, so N is already encoded. |
| D5 | A non-zero `iverilog` exit status counts as COMPILE_ERROR even when no log line contains "error". | Keeps classification total; the harness would otherwise fall through to `R`. |
| D6 | A3 uses two negative controls: a module with the correct ports and no logic (`empty_header`), and an empty module with no ports (`empty_module`). | The first gives a MISMATCH, the second a compile error; both must fail. |
| D7 | A6 also flags a model digest of `unreachable` or `unknown`. | A real run must record digests; without a server the manifest is incomplete. |
| D8 | Added planted-truth checks P1–P7. | They compare pipeline output with exact values known from stub definitions (Section 12 had only oracle and negative controls). |
| D9 | Measured Yosys cost: about 0.75 s per run on one CPU (252 s for 336 runs), so Section 6.5's "cheap" needs qualifying. | Expect roughly 10–20 min per model for the Yosys stage on one CPU in a real run; use `--jobs`. |
